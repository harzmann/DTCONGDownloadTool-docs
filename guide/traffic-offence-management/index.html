    Traffic-offence management¶

    This module supports fleet managers with the administrative processing of German traffic offences. It does not replace legal or privacy advice and makes no automatic decision about guilt, liability or the driver.

    Workflow¶

    While the Traffic offences workspace is open, it refreshes the review inbox and case overview from the database every 15 seconds. Selection and scroll position are preserved, and newly added review items are announced in the action row. Refreshing stops completely when the tab is switched away from or closed. The UI never triggers its own IMAP poll; it only displays results already imported by the worker.

    Authority documents are accepted by upload, a watched import folder or a dedicated IMAP mailbox. Original files and messages are retained unchanged with a SHA-256 checksum. Text PDFs are read locally; images and scans can be processed with a locally installed Tesseract service. When a document creates a new case, its document type and date, authority, reference, registration, offence time and location, vehicle and response deadline must all be confirmed regardless of document type. When a document is assigned to an existing case, the review shows only the assignment, the required document date and the optional response deadline; the other case fields are hidden and are not requested again.

    Once confirmed, the review-inbox item is immutable. View or a double-click opens the already linked case and cannot create a second case or assign the original to another case.

    New and unprocessed review-inbox entries are highlighted with red text. Confirmed, rejected or already case-linked entries use the normal text colour. When a row is selected, the shared blue-and-white selection appearance always takes precedence.

    Case workspace and workflow¶

    Each case opens in its own workspace tab. A localised progress indicator covers Case reviewed, Identify driver, Request driver response, Prepare authority response, Record dispatch and Close case. It consists of six cells inside one surrounding frame: completed steps are green, the active step is red and pending steps are yellow. All six cells are green after the case has been closed. The current task and all available actions are derived centrally from the domain workflow state. Actions that are not yet allowed remain disabled. The workspace reads worker and IMAP results from the database every 15 seconds while preserving selection and scroll position.

    Below Case: [case number] - [authority reference], the following actions are available according to status and permissions: Edit, Refresh driver evidence, Confirm driver, Send driver request, Create fillable driver PDF, Prepare authority response, Record dispatch, Add document, Close case and Cancel case. Case data shows the confirmed master data. Edit opens a modal dialog; authorised users can save changes only after entering a reason. Previous and new values are audited. Changing the vehicle or offence time recalculates driver evidence, while a changed response deadline updates the document-specific due item.

    Driver identification shows candidates and evidence with source, priority, validity interval, confidence and conflict state. An active person must be explicitly confirmed. If the evidence chain from tachograph data, telematics, dispatch and the default driver yields no candidate, any active person can be assigned manually with a reason. An automatically identified driver can also be overridden by the person who actually drove; this likewise requires a reason. Manual and overriding decisions remain visible as separate evidence and are audited.

    Driver communication contains versioned requests and their related responses. The confirmed driver, email address, SMTP configuration and HTTPS portal are checked before sending. Portal link, return reference and fillable PDF are prepared transactionally and sent asynchronously. The case changes to “Driver response pending” only after SMTP succeeds. Failures remain visible and are included in the daily fleet-manager report. An intentional resend creates a new version and return reference.

    Portal, PDF and email responses remain bound to the person and communication that were actually addressed. Raw data and extracted proposals are never overwritten. Review stores a separate confirmed snapshot. Without a preselected default, the reviewer must choose Continue driver identification or Prepare authority response; even an affirmative response never causes an automatic transition.

    Authority response creates a PDF only from facts that the reviewer explicitly selects from previously confirmed data. Creating the PDF is not dispatch. Record dispatch captures the answered authority document, channel, time, optional evidence and note. Only the due item for the selected document is completed; any other open document deadline remains open.

    The Documents tab contains the unchanged source document and all later additions, such as an objection, legal-protection confirmation or completed witness questionnaire. Internal document types distinguish driver declaration form, authority response and dispatch evidence. Later files are archived with a checksum in the same case file and never replace or modify the source document.

    The Emails tab combines inbound messages correlated through IMAP and recorded outbound email in one chronological timeline. Sender, recipient, subject, status and readable message text therefore remain directly traceable from the case.

    Audit shows revision-safe changes and workflow decisions. A regular close is allowed only after an authority dispatch has been recorded and no unreviewed driver response or open document deadline remains. Closing with open items requires the dedicated traffic_offences.close_override permission and a reason; open due items are archived rather than incorrectly completed. Cancellation also requires a reason. Closed and cancelled cases are read-only and cannot be reopened in version 1.

    Driver identification evaluates only time-overlapping evidence in this order: M data, telematics driver history, dispatch and the historical default driver. A card in the co-driver slot or an unconfirmed card-to-person link is not driver evidence. Every assignment requires confirmation; overriding the highest-ranked proposal requires a reason.

    When creating a case, the offence time is entered through a date-time picker. It defaults to the current time, displays date and time according to the signed-in user's region, and stores the instant normalized to UTC together with its local time context.

    When assigning a historical default driver, the validity start is selected from a calendar. The date picker defaults to the current date and displays it in the signed-in user's regional format.

    Drivers may respond through an internal HTTPS form, a personalised fillable PDF or free-form email. Vehicle use, allegation statement, address, comment and attachments are stored separately and always require review. An address supplied for a case never changes personnel master data automatically.

    Deadlines and notifications¶

    The dedicated Traffic-offence deadlines view is nested directly below Traffic offences in fleet navigation; the opened workspace tab uses the same title. It refreshes whenever it is opened and after an authority document is confirmed. It displays only time-based domain data such as authority, reference, case, vehicle, confirmed driver, workflow and document status, due date and remaining days. Odometer, odometer source, target or remaining kilometres and distance-based filters are not used in this view. The first visible deadline is selected as the current row on the initial load. Light status highlights use contrasting dark text, while the current row uses the same white-on-blue appearance as the personnel deadline evaluation. Selection and scroll position are retained across asynchronous reloads without taking input focus away from navigation or filters. Double-clicking opens the related case.

    Every confirmed document with a deadline receives a separate managed due item. Changing the date updates that item; only the recorded reply for that document completes it. Cancelled documents and documents confirmed as having no deadline archive the item with a reason.

    The daily fleet-manager report contains pending driver declarations, replies due today or soon, overdue cases and technical errors. Addresses, free text, offence details, document contents and attachments are never included in the report email. The optional 2x2 widget is added only from the widget catalogue and does not modify existing layouts.

    Operations¶

    The driver portal must be published with HTTPS inside the intended LAN/VPN. Access tokens are stored only as hashes, exchanged once for a short-lived session and protected by CSRF validation. Pro uses SQLite and the in-process worker; Enterprise uses PostgreSQL and FleetMiraWorker exclusively.

    Demo data¶

    The distributed demo database contains no traffic-offence cases. If required, the optional idempotent seed python scripts/seed_traffic_offence_demo.py creates 20 penalty notices clearly marked as fictitious and not payable. Each generated case is assigned to an existing vehicle, includes a synthetic enforcement-camera image and is registered with a document reference and test deadline in both traffic-offence management and the document archive.
