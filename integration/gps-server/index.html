    GPS-server.net integration¶

    The GPS-server.net integration is available in Pro and Enterprise. It exclusively uses the read-only User API 1.20. Basic has no telematics functionality.

    Scope¶

    FLEET Mira synchronises GPS-server objects, current positions, location messages, routes, events and human-readable addresses. The IMEI is the external object identifier. Its link to a FLEET Mira vehicle is time-bound, so tracker replacements retain the correct historical assignment.

    Vehicles are suggested first by a unique normalised VIN and then by a unique registration. An administrator confirms the assignment. Provider fields never update local vehicle master data automatically.

    The vehicle record's Master data tab shows the latest reliable odometer reading with source and quality, plus the last known human-readable position using the signed-in user's regional format. Edit vehicle opens the same modal master-data form as the vehicle list. For an active assignment, Open telematics opens a dedicated workspace that is reused per vehicle.

    Configuration¶

    1. Open Administration → Telematics → GPS-server.net. Additional telematics providers are added at the same level as separate subtabs.
    2. Enter a name, the actual HTTPS base URL, the GPS-server time zone and, optionally, the expected GPS-server username.
    3. Pro: enter the User API key. It is protected per user with Windows DPAPI outside the database.
    4. Enterprise: provision the User API key on the FleetMiraWorker server. PostgreSQL stores only the credential_ref.
    5. Test the connection and start the first synchronisation.
    6. Review the reconciliation list and assign every GPS-server object to a vehicle.
    7. Select sensor, GPS or unknown as the odometer type for each object when the API does not identify it unambiguously.

    The base URL is never inferred from the key or hard-coded to a particular GPS-server host. FLEET Mira appends the User API path /api/api.php?api=user.

    Creating a vehicle from a GPS-server object¶

    1. Run at least one object and position synchronisation.
    2. Select exactly one object under Administration → Telematics → GPS-server.net → Vehicle assignment.
    3. Choose Create vehicle from GPS-server object. The command is available both as a button and from the table row's context menu.
    4. Review and complete the internal number, registration, VIN, vehicle type, manufacturer and model.
    5. Save the record. FLEET Mira creates the vehicle, links the object for the configured initial backfill period (30 days by default), and reassigns stored positions, events and odometer observations within that period. A different earlier vehicle assignment is never overwritten.

    Comma-separated message parameters are evaluated individually. If the latest position message contains a formally valid 17-character VIN in io256, it is prefilled as a provider observation. This never changes existing local vehicle master data. Differences between the object master and io256 are explicitly flagged for review. If a vehicle with the same VIN or registration already exists, use Assign selected object; FLEET Mira will not create a duplicate.

    Look up manufacturer and model online is an optional one-off request. Only after confirmation is the VIN sent to the official US NHTSA vPIC service. The service focuses on vehicles intended for the US market, so European vehicles may return only manufacturer data or no reliable model. The result therefore remains an editable suggestion and requires administrative review before saving.

    Vehicle record and telematics workspace¶

    The Telematics: [vehicle no.] – [registration] workspace contains:

    • Current location, with human-readable address, measurement time, live request and a native OpenStreetMap map,
    • Route history, with From/To selection and the last seven days as its default,
    • Positions, a combined evidence list for tachograph and telematics data,
    • Events from the synchronised telematics history.

    Route history initially uses local data. Refresh displays that data immediately and only loads uncovered intervals in the background. After confirmation, Reload from provider bypasses the cache and is restricted to users with telematics.reconcile. Pro runs the request in its in-process worker; Enterprise only enqueues PostgreSQL jobs for FleetMiraWorker. Waypoints are stored immediately after the message request; optional route aggregation and larger geocoding batches do not block their display. The latest position is reverse-geocoded specifically. Telematics points are joined chronologically by straight segments. Gaps longer than 30 minutes are dashed; FLEET Mira neither road-snaps nor invents waypoints. Tachograph positions can be displayed as differently coloured reference markers but never form the route line. With more than 20,000 telematics points, the warning to narrow the period remains visible while the map still renders a chronological, database-side overview of at most 5,000 representative points, including the start and end. Sensor parameters are not loaded for this query. Technical zero coordinates and invalid values do not affect the map extent or route.

    The vehicle record's Positions tab globally sorts tachograph and telematics evidence and provides a source filter. With Tachograph selected, Refresh only reloads the local database. With All or Telematics, it starts a targeted position catch-up for the assigned vehicle and selected period; Enterprise hands the same request to FleetMiraWorker. Retrieval and storage progress is visible in the global status bar. Evidence from different sources remains separate even when time and coordinates match. Without the licence feature or telematics.read, the list contains tachograph data only.

    The GPS-server.net web interface is not embedded. GPS-server.net excludes embedding its map in its FAQ. FLEET Mira therefore uses locally synchronised data and the native map, preserving permissions, retention and Enterprise worker boundaries.

    On the Enterprise worker server, the key is requested securely without a command-line argument or log output:

    FLEET-Mira.exe --telematics-secret-action set --telematics-credential-ref "<connection-id>"

    Use status to check provisioning and remove to delete the key. The Windows service does not need to be reinstalled afterwards.

    Synchronisation and odometers¶

    Objects are synchronised daily. Current positions and position/event catch-up run every five minutes by default. Successful historical intervals, including empty responses, are registered as cache coverage. Repeated requests for completed periods therefore use only the database; mixed periods are reduced to their missing sections. The open end receives a two-minute overlap. Provider windows are at most 24 hours. Failed or partial responses are not marked as completely covered. The connector normalises both object responses and the seven-field position arrays returned by User API 1.20. History and date selection are limited to the local start of day 28 days ago through the current time.

    In Pro, the Qt timer triggers one serialised in-process worker thread and immediately returns control to the UI. HTTPS requests, retries and larger history imports therefore run in neither the sign-in thread nor the UI thread. Periodic and manually requested telematics operations in the same Pro installation share one execution lock. Position messages are stored in backend-neutral transactions of 500 records rather than opening and committing a database connection for every waypoint. Normal application shutdown waits for the active pass in a controlled manner.

    Pro uses exactly one telematics writer because additional SQLite worker processes would increase write locking and API load. Enterprise executes this work exclusively in the separate FleetMiraWorker. Its PostgreSQL queue supports leases and multiple worker instances, but one instance remains the recommended GPS-server.net setup. Horizontal scaling only becomes useful when jobs are partitioned by connection and provider limits are observed.

    The last real odometer value before local midnight is projected as the daily value when it is no more than 24 hours old. FLEET Mira does not interpolate values. Raw observations within one day are compacted into a candidate containing the latest value and measurement time, count, minimum and maximum. A newly received real sensor observation is already shown with warning status in the vehicle record until regular daily projection and validation have run. For Teltonika data, the connector recognises the GPS-server odometer including the corresponding io389 (kilometres) and io16 (metres) parameters. Priority is:

    1. signed M midnight reading,
    2. approved manual reading,
    3. GPS-server sensor reading,
    4. C-file reading,
    5. GPS-server GPS reading,
    6. unknown telematics source.

    GPS-server readings are not signed M events. Decreasing values and implausible daily distances are marked as conflicts.

    Enterprise webhook¶

    Enterprise can receive events through this TLS-protected reverse-proxy path:

    /api/telematics/webhooks/{connection_id}/gps-server/{secret-token}

    The endpoint accepts GET and application/x-www-form-urlencoded POST. A secret URL token, the expected GPS-server username and an optional IP allowlist protect it because GPS-server does not document a webhook signature. Conflicting GET and POST values are rejected.

    The webhook only acknowledges receipt and queues an API catch-up job. Positions and odometer values are subsequently confirmed through the User API. Raw webhook payloads are deleted after 30 days.

    Security and operations¶

    • Use only a User API key, never a user password or Server API key.
    • API keys, complete URLs and query strings must never be logged.
    • Outbound HTTPS connections use the native Windows certificate store. Certificate and hostname verification remain enabled; the Windows Chain Engine can securely complete an incomplete server chain.
    • Restrict production keys to the worker IP where possible.
    • Detailed positions are retained for a fixed 28 days from the local start of day. Each object's latest known state, daily odometer readings, events and audit data are retained. Sensor parameters remain losslessly available as compressed zlib-json-v1 during the detail period.
    • ACTION_REQUIRED indicates key, permission, certificate or response-format problems. DEGRADED indicates temporary network or server failures.
    • If Address is being resolved remains visible, inspect the latest telematics_geocode_position run. Depending on the GPS-server installation, GET_ADDRESS can return JSON or plain text; both formats are supported.
    • Remote commands, Location API, Server API, media and the device protocol are outside this integration.
